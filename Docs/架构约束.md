# 架构约束

> 一句话：**四层 + `cfg` 的边界过去只是命名空间约定，现在是 asmdef 边界 —— 越界会编译不过，而不是"只能靠人守"。**
> 本文件是那份拓扑的唯一权威描述；`Tools/compile-gate.ps1` 是它的机器判据。

## 2 · 依赖方向铁律

```text
              ┌──────────────────────────────┐
              │      DeepseaOil.Presentation │   ← 只有它能引全部
              └───────────────┬──────────────┘
                              │
              ┌───────────────▼──────────────┐
              │        DeepseaOil.Logic      │
              └───────────────┬──────────────┘
                              │
              ┌───────────────▼──────────────┐        ┌───────┐
              │        DeepseaOil.Data       │───────▶│  cfg  │
              └───────────────┬──────────────┘        └───┬───┘
                              │                           │
              ┌───────────────▼──────────────┐        ┌───▼───────────────┐
              │    DeepseaOil.Foundation     │        │   Luban.Runtime   │
              └──────────────────────────────┘        └───────────────────┘
                    （谁都能引它，它谁也不引）
```

- 箭头是**编译期引用**，不是"建议"。反向的引用写进 asmdef 会被拓扑守卫拦下；写进代码会 CS0234。
- `Foundation` 是唯一的"叶子"：任何人可以引它，它不能引任何人。
- `cfg` 只服务 `Data`，不得反过来知道 `Data` / `Logic` / `Presentation` 的存在。

## 3 · 编译器现在能挡什么（以及挡不住什么）

**能挡（实测）：**

| 越界形态 | 报错 |
| :-- | :-- |
| 代码里碰没引用的层（含全限定名） | `error CS0234`（"命名空间 DeepseaOil 中不存在类型或命名空间名 Data"） |
| asmdef 里声明反向引用 | 编译门的拓扑守卫：`守卫：发现反向依赖` |
| 两个程序集互相引用 | MSBuild `error MSB4006: 依赖项关系图中存在循环依赖项`（Unity 里就是 `Cyclic references`） |
| references 里写错名字 | 编译门：`守卫：这些引用解析不到（会变成 CS0246）` |
| 引用了 `internal` 成员 | `error CS0117 / CS0122` |
| **漏写一条 references 而靠"上一层替我带进来"** | `error CS0012`（"类型 X 在未引用的程序集中定义"）＋ 连带的 `CS0117`。见下面 §3.1 |

### 3.1 🔴 asmdef 的 references **不传递**（踩过一次的坑）

Unity 的 asmdef 引用**不是**传递的：`Tests.Scene → Presentation → Foundation` 这条链**不会**让 `Tests.Scene` 看见 `Foundation` 的类型。

实测形态：`Assets/Tests/Scene/TestAudio.cs` 写 `GameRoot.Instance`。`Instance` 是 `GameRoot` 从 `DeepseaOil.Foundation` 的 `Singleton<T>` **继承**来的 —— 判定这个成员存不存在必须看见基类所在程序集，于是漏写 `DeepseaOil.Foundation` 时报：

```text
error CS0012: 类型"Singleton<>"在未引用的程序集中定义。必须添加对程序集"DeepseaOil.Foundation"的引用。
error CS0117: "GameRoot"未包含"Instance"的定义
```

**报的是"成员不存在"，真因是"少了一条 references"** —— 别顺着 CS0117 去改代码。

⇒ 规矩：**用到的每个类型，其定义所在程序集都要显式写进 `references`**，包括基类、接口，以及公开签名里出现的类型（`TMPro` / `UnityEngine.UI` / `Unity.InputSystem` 同理）。

编译门为此把 MSBuild 的 `ProjectReference` 传递性**关掉**（生成的临时工程里写 `<DisableTransitiveProjectReferences>true</DisableTransitiveProjectReferences>`），否则门会因为 MSBuild 默认传递而比 Unity 宽松、给你假绿。

**挡不住（别指望它）：**

- 层内**各组之间**的依赖（`Logic/Actor` 引 `Logic/Wave` 之类）—— 那仍是命名空间约定，见 `Assets/Scripts/Presentation/ISceneRoot.cs` 顶部的命名规则。
- `Logic` 的"纯逻辑"纪律（不许 `MonoBehaviour`、不许碰场景对象）—— asmdef 管不了，`DeepseaOil.Logic` 照样能引 `UnityEngine`（它需要 `Vector2` / `Mathf`，所以 `noEngineReferences` 必须留 `false`）。
- `Data` 只读、`GameRoot` 唯一单例、"只有一个逐帧驱动入口"这类运行期纪律 —— **没有任何机器判据**，只写在 `AGENTS.md` 与本文档里。（原先扫源码文本的 `Assets/Tests/Tools/收口一致性Tests.cs` 已删：那种断言改个措辞、加个白名单外的合法调用就红，守不住真回归，只挡进度。）
- 拓扑守卫的黑名单是**手写维护**的（`Tools/compile-gate.ps1` 里的 `$forbiddenRefs`）。新增层时要同步加，否则新层没人守。

## 4 · 三条雷区的实测结论

### A · `Foundation` 绝不能引 `Data`

历史遗留是 `IStateHost.Config` 返回 `CharacterConfig`。**当前代码里这个属性已经不存在**：`Assets/Scripts/Foundation/IState.cs` 的 `IStateHost` 只有 `Motion` / `MoveTowards` / `BrakeTowards` / `SnapVelocity`，`Config` 口留在 `Logic` 的 `IActorMotor`（`Logic/Movement/IActorMotor.cs`，它本来就允许引 `Data`）。

实测：加上 `DeepseaOil.Foundation.asmdef`（`references: []`）后 **11 个 .cs 零错误编译通过**，没有 CS0246 ⇒ **不需要改任何代码**。（若将来真要让 `IStateHost` 暴露配置，正确做法是给接口加泛型参数或换成 `Foundation` 自己的值类型 —— 见 `MotionParams` 的既有取舍，**不要**给 `Foundation` 加 `Data` 引用。）

### B · `cfg.asmdef` 必须在 `Scripts/Generated/`，**不能**放 `Generated/Config/`

`Assets/Scripts/Generated/Config/` 是 Luban 的**镜像覆盖区**：`Assets/Editor/LubanImport.cs` 的 `MirrorCopy()` 会删除目标目录里"暂存区没有的**一切非 `.meta` 文件**"（`MirrorCopy` 的删除循环；`LubanProject.cs` 顶注与 `ConfigWorkspace/AGENTS.md` 都写明"多余文件删除"）。

⇒ 把 `cfg.asmdef` 放进 `Generated/Config/`，**下次导表就会被静默删除**，`Generated/Config/**` 随即退回 `Assembly-CSharp`，整条边界无声塌掉（不报错、不警告）。

因此 `cfg.asmdef` 放在**上一级** `Assets/Scripts/Generated/`：该目录**不是**镜像目标，文件安全；它覆盖 `Generated/Config/**`，而 `Generated/Input/` 有自己的 asmdef 所以被自动排除（Unity 规则：最近祖先 asmdef 胜出）。编译门有专门守卫拦这条路：

```text
守卫：Assets\Scripts\Generated\Config 是导表镜像覆盖区，asmdef 下次导表必被删除 —— 应放在 Generated/
```

### C · Luban 的真实程序集名是 `Luban.Runtime`

`Assets/Luban.Runtime/Luban.Runtime.asmdef` 的 `name` 就是 `Luban.Runtime`（不是 `DeepseaOil.Luban.Runtime`）。引用时按真名写。

🔴 **不要**装 Luban 的 UPM 包：两份 asmdef 撞名 `Luban.Runtime` 会报 `Assembly with name 'Luban.Runtime' already exists`，**整个工程所有程序集都编译不出来**。编译门为此加了重名检测（`asmdef 重名 —— 撞名会导致整个工程所有程序集都编译不出来`）。

## 5 · 为过边界做的代码改动（仅此两处）

| 文件 | 改动 | 原因 |
| :-- | :-- | :-- |
| `Assets/Scripts/Data/Asset/AssetModule.cs` | `internal static bool IsInitialized` → `public static bool IsInitialized` | 它被 `Presentation` 的 `EffectModule` / `GameRoot` 用了 4 处。上一版靠"全工程一个程序集"白拿，分程序集后是 `CS0117`。同组另外 6 个 `internal` 口（`Cache` / `Scheduler` / `Lifecycle` / `Failure` / `CacheHits` / `CacheMisses`）**刻意留 internal**：它们只服务同程序集的 `DataMetrics` |
| `Assets/Tests/Scene/TestChangeScene.cs` | 删掉 `using Unity.VisualScripting;` | 该 using 是死引用（文件只用了 `MonoBehaviour` / `Collider2D` / `EventBus`）。删掉后测试程序集就不必为一个没人用的命名空间挂 `Unity.VisualScripting.Core` 引用 |

**没有**为了让边界通过而扩大任何层的 references —— 这一点是验收判据：`Presentation` 之外的四层 references 里都不该出现"为了让它编过"而加的包。

## 6 · 怎么验证

```powershell
pwsh Tools/compile-gate.ps1              # 生成 + 编译 + 拓扑守卫（目标 0 error / 1 warning）
pwsh Tools/compile-gate.ps1 -Topology    # 额外打印程序集拓扑表
pwsh Tools/compile-gate.ps1 -NoTopologyGuard   # 只跳过守卫（调试用）
```

编译门为**每个 asmdef 单独生成一个临时工程**并按真实引用图串 `ProjectReference`，所以它验的就是 Unity 将要做的事（含循环依赖）。四条守卫：① 目录→应有 asmdef 名；② 反向引用黑名单；③ asmdef 重名；④ asmdef 不在镜像覆盖区。

反向依赖的**负向验证**（2026-10，本文件成文时实测）：

| 注入的违规 | 结果 |
| :-- | :-- |
| `Foundation` 里写 `DeepseaOil.Data.AssetModule.IsInitialized` | `error CS0234`，退出码 1 |
| `DeepseaOil.Foundation.asmdef` 加 `DeepseaOil.Data` | `守卫：发现反向依赖`，退出码 1 |
| `Foundation` ↔ `Data` 互引 | `error MSB4006 … 循环依赖项`，退出码 1 |
| `Generated/Config/` 下放 asmdef | `守卫：…镜像覆盖区…下次导表必被删除`，退出码 1 |
| `DeepseaOil.Tests.Scene` 漏写 `DeepseaOil.Foundation`（`GameRoot.Instance` 的基类在那儿） | `error CS0012` ＋ `CS0117`，退出码 1 —— **关掉 ProjectReference 传递性之后**才复现得出，这就是 §3.1 的由头 |

## 7 · 改动规矩（checklist）

**加一个新层 / 新程序集时：**

1. asmdef 落在**该层目录自己**下面（别落在会被覆盖的生成物目录里）。
2. `Tools/compile-gate.ps1` 的 `$expectedAsmdefs` 加一条（目录 → 应有 asmdef 名）。
3. 同文件的 `$forbiddenRefs` 给它加反向黑名单 —— **不加就等于没人守**。
4. `Docs/目录说明.md` 的目录树补上 asmdef 文件，`README.md` / `AGENTS.md` 的口径同步。
5. `pwsh Tools/compile-gate.ps1` 必须 0 error / 1 warning。

**给现有层加一条引用时：** 先问"这是不是反向依赖"。是 ⇒ 改设计（端口 / 值类型 / 泛型），不是 ⇒ 加进 asmdef 并在本文件 §1 的表里更新。**永远不要**为了让某层编过而把 `Data` 塞给 `Foundation`。引用要**写全**：Unity 不传递，基类 / 接口 / 公开签名里出现的类型的程序集都得写（§3.1）。

**改表 / 导表后：** 生成物目录会被镜像覆盖，`cfg` 与 `DeepseaOil.Generated.Input` 的 asmdef 都不在其中 —— 但如果你在 `Generated/Config/` 新建了任何手写文件，它下次导表必丢，编译门会红。

## 8 · 还没做的（后续可收紧）

- 拓扑守卫只守"层与层"这一张粗粒度表，不守层内各组；层内仍靠命名空间约定与人。
- `Assets/Scripts/Generated/` 目录本身仍是"机器生成"语义的目录，现在里面有了一个手写的 `cfg.asmdef`。这是 §4-B 的直接后果；如果哪天给 Luban 换输出路径（不再镜像覆盖 `Generated/Config/`），应该把 `cfg.asmdef` 挪回 `Generated/Config/` 并撤掉对应守卫。
