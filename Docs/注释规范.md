# C# 注释规范

> 适用范围：`Assets/Scripts/**` 下的**手写** C# 文件。
> 不适用（禁改，见 `AGENTS.md` §3）：`Assets/Scripts/Generated/**`、`Assets/StreamingAssets/Luban/**`。
>
> 机器判据：`pwsh Tools/comment-lint.ps1`（退出码 0 = 通过）。
> 本文件是注释口径的**唯一权威**；`Tools/注释精简规则.md` 里的旧口径已作废（见文末 §8）。

---

## 0. 为什么要有这份规范

注释是本工程唯一**没有机器判据兜底**的产物：写多了不会编译失败、不会测试变红、不会有人 review 到。
于是它必然单调膨胀——实测数据：

| 时间点 | 手写文件 | 注释有效字符 | 代码行 | 密度（字符/代码行） |
|---|---|---|---|---|
| 第一次清理后（`e2f08be`） | 166 | 53,893 | 10,044 | 5.37 |
| 此后若干轮开发（`e0b28cc`） | 172 | **69,704（+29%）** | 10,868 | **6.41（+19%）** |
| 第二次清理后（Round-2） | 172 | 57,233 | 10,868 | 5.27 |

代码只长了 8%，注释长了 29%。所以本规范的重点**不是教怎么写注释，而是设一条能自动拦住的预算线**。

---

## 1. 唯一判据（每次想写注释，先问这一句）

> 这条注释是不是在防止某个人做出一个「**编译器不会拦、测试不会红、只表现为手感 / 观感 / 性能错**」的改动？

- **是** → 写，并且压成**一行**。
- **否** → 不写。

写不出来"删了会有人做错的具体场景"，就是不该写的注释。

---

## 2. 必须写（白名单）

只有这几类信息值得占用注释预算：

| # | 类别 | 本仓实例 |
|---|---|---|
| 1 | **跨层 / 跨程序集约定与调用时序** | 「物理帧登记（表现层换格时），本类 Tick 统一结算 —— 效果施加因此只有一个相位」 |
| 2 | **配表契约**：表名 + 列名 + 效果号含义 + 退役字段承接 | 「`tile_effect` 表的档位在数据层已按 `effectValuePos` 定值，本类只消费结果」 |
| 3 | **单位与量纲** | 「value1 单位是格，ApplyKnockback 收速度（单位/秒）」 |
| 4 | **魔法值的来源** | 「必须小于 0.5：被测对象在正中，越过中线就被盖住」 |
| 5 | **非直觉算法的依据** | 「总位移 ≈ 冲量/衰减率，故乘回衰减率」 |
| 6 | **接口契约**：返回 null / false 的语义、null 参数的多种含义 | 「返回 false：落在地板外、规则不给状态、或结果就是当前状态」 |
| 7 | **已知坑与硬约束** | 「与 `EnemyTuning.knockbackDecay` 同源，那边改了这边要跟」 |
| 8 | **静默失败** | 「未实现的效果种类必须出声，不许 `default: return` 吞掉」 |
| 9 | **性能约束** | 「字符串只在首次命中时构造，Supported 分支直接 return，无分配」 |

压缩原则：**原意不动，压成一行短句**。删的是论证过程，不是结论。

---

## 3. 禁止写（黑名单 = 四类删减理由）

| 代号 | 含义 | 本仓典型形态 |
|---|---|---|
| `重复复述` | 把代码/命名已经说清的事再说一遍 | `/// <summary>合法格，只有登记过的格能被转换</summary>` 挂在 `private bool IsLegal` 上；`<param name="row">表行</param>` |
| `背景论证` | 为什么当初这样写、未采纳方案、调试故事、实测叙述 | `🔴 这里曾经再查一次表并钉死第 1 档…（实测）`、`当时的理由…`、`收口前…`、`D4/D7/D9` 长篇推导、`<para>` 堆砌的"为什么不那样写" |
| `排版标签` | XML 排版 / 交叉引用标签，以及跨行注释块 | `<c>`、`<para>`、`<b>`、`<see cref>`、多行 `<summary>` / `<remarks>` |
| `冗余修饰` | 不影响语义的形容词、连接词、重复限定 | `注意`、`请务必`、`这里`、`本类`、`即`、`从而`、`非常`、`刻意` |

另外两条：

- **进度叙事不进代码**：`TODO` / `待办` / `将来会做` → 写到 `Docs/待办.md`。
- **装饰性分隔横线不许有**：
  ```csharp
  // ─────────────────────────────   ← 删
  // IActorLedger：读                 ← 这一行有信息，留成单行
  // ─────────────────────────────   ← 删
  ```

## 4. 形式硬规则

1. **XML 标签白名单只有 `<summary>` 和 `<remarks>`。**
   出现以下任何一个都算违规，必须**物理删掉标签本身、保留其中的文字**：
   `<c>` `<para>` `<b>` `<i>` `<em>` `<strong>` `<paramref>` `<param>` `<returns>` `<list>` `<item>` `<code>` `<br>` `<p>` `<see cref>` `<seealso>` `<inheritdoc>` `<example>` `<exception>` `<value>`
   - `<see cref="Foo"/>` → 写成纯文本 `Foo`。
   - 泛型写法 `<see cref="Pool{T}"/>` → 写成 `Pool`（别留下 `<T>`，它会被判成标签）。
   - **XML 转义只在"标签已被删掉"之后才还原**：`&lt;` `&gt;` `&amp;` → `<` `>` `&`。
     仍留在 `<summary>` / `<remarks>` **内部**的转义必须原样保留（例：`<summary>Duration 秒且 &lt;=0 表示永久</summary>`），
     改成裸 `<` 会让 `///` 注释的 XML 非法。
2. **注释一律单行**：一个 `<summary>` / `<remarks>` 元素必须**在同一行内开闭**。
   禁止这种拆行写法：
   ```csharp
   /// <remarks>
   /// 正文……
   /// </remarks>
   ```
   （相邻的 `/// <summary>…</summary>` 与 `/// <remarks>…</remarks>` 是**两条**独立注释，合法。
   `comment-lint` 的判定方式是"单行内标签开闭是否配平"。）
3. 删掉整行注释后，**连续空行收敛到最多 1 行**。
4. `#region` / `#endregion`、预处理指令、`using` 不许当注释用；不许用它们做分区装饰。
5. 中文保持中文，不中英混排同一句。
6. **改注释时不许动代码**：不合并 / 不拆分行、不改缩进、不改标识符、不改字符串字面量
   （`[Tooltip("…")]`、`[Header("…")]`、`[SerializeField]` 后面的中文串**是代码**）。
7. 不许改文件的行尾风格（CRLF / LF）与 BOM 有无。

## 5. 预算与守卫（机器判据）

### 5.1 口径

**注释有效字符数**：逐行取注释正文，剔除 `//`、`///`、`/* */` 标记；行首行尾空白不计、换行符不计；
其余（文字 / 标点 / 空格 / XML 标签）全部计入。

> 注意这条口径的两个推论：① 删掉一整个 `/// <summary></summary>` 行比改写它更省，
> 光标签壳就值 19 个字符；② 换成密度看，**文档注释特别密的接口/工具类天然吃亏**，
> 所以预算按文件登记，不搞一刀切。

### 5.2 预算表

`Tools/comment-budget.json` 登记**每个文件的注释字符上限**。

- **`-Mode seal` 写入的是"封印当时的实际值"**，所以每个文件的额度天然是**净零**的：
  **想加注释，就得先删等量的注释。** 这是本项目对"注释只降不升"的落地方式——
  它不是"留一点余量慢慢涨"，而是"加一个字就报错"。
- 确需**净增**（该文件真的承担了新复杂度）时：跑 `-Mode seal`，让预算上调出现在 diff 里，
  并在 PR 描述里写明理由。**日常开发不要 seal**，否则等于把自己的超标改成"合法"。
- **新增文件**未登记时，按密度上限 `densityCap`（默认 **5.37** 字符/代码行）判定；
  合入时随 `-Mode seal` 正式登记。
- 文件被删除 / 改名后预算表会出现**孤儿条目**（脚本会 WARN），随下次 `seal` 清掉。

### 5.3 命令

```powershell
pwsh Tools/comment-lint.ps1                          # 全量判定：预算 + 标签，违规 exit 1
pwsh Tools/comment-lint.ps1 -Mode report -Top 30     # 逐文件 预算/现值/余量/密度 表（按超支排序）
pwsh Tools/comment-lint.ps1 -Mode tags               # 只查 XML 标签白名单
pwsh Tools/comment-lint.ps1 -Mode verify -Base e2f08be   # 证明「只改了注释、代码零改动」
pwsh Tools/comment-lint.ps1 -Mode check -StagedOnly  # 只看本次改动的 .cs（CI / 提交前）
pwsh Tools/comment-lint.ps1 -Mode seal               # 清理验收后重新封印预算（会 diff 出预算变化）
```

### 5.4 什么时候必须重跑 seal

只有一种情况：**你刚刚做完一轮被批准的注释清理**。
日常开发、加功能、写新类，**都不要 seal**——那等于把自己的超标改成"合法"，正是本规范要防的事。

## 6. Definition of Done

动了 `.cs` 文件（哪怕只动注释）就要过这四条：

- [ ] 1. `pwsh Tools/comment-lint.ps1` → 退出码 0（`LINT OK`）
- [ ] 2. 动了注释时：`pwsh Tools/comment-lint.ps1 -Mode verify -Base <上一个已验收提交>` → `VERIFY PASS`
- [ ] 3. `pwsh Tools/compile-gate.ps1` → `0 error / 1 warning`（唯一基线警告：`SaveService.cs:14` CS0649）
- [ ] 4. 没有触碰 `Assets/Scripts/Generated/**`、`Assets/StreamingAssets/Luban/**`

## 7. 反例对照（本仓真实片段）

### 7.1 多行 `<remarks>` 的"设计论证" → 压成一行结论

```csharp
// ✗ 前（102 字符）
/// <summary>诊断面板共用的 GUI 口径：放大倍数按屏幕收口 ＋ 面板命中矩形</summary>
/// <remarks>
/// 1920×1080 下 IMGUI 默认 12px 字号太小，故整体放大；但面板占的是固定像素、世界内容按分辨率缩放，
/// 放大后的左上角面板会盖住被测对象（木桩 / 棋盘），点下去还会被判成点面板，故倍数必须按屏幕收口。
/// 不包 `#if`：不进正式构建的 Harness 与仍会进构建的 MovementDebugPanel 要用同一份算法。
/// </remarks>

// ✓ 后（60 字符）
/// <summary>诊断面板共用的 GUI 口径：放大倍数按屏幕收口 ＋ 面板命中矩形</summary>
/// <remarks>放大后的面板会盖住被测对象、点击还会被面板判定吃掉，故倍数必须按屏幕收口。</remarks>
```
删的是「1920×1080 下 IMGUI 默认 12px」这段**论证过程**，留的是结论（必须收口）+ 理由（会盖住对象）。

### 7.2 变更史 + 实测叙述 → 只留约束

```csharp
// ✗ 前
/// <remarks>
/// 🔴 这里**不再**把 seconds&lt;=0 替换成一帧 Δt：表里没填时长就是"只要在格子上就持续生效"，
/// 窗口交给消费者（StatusGroup）按自己的拍决定。生产者这一侧替换等于把窗口钉成渲染帧 0.0167s，
/// 而消费者按物理帧 0.02s 扣 —— 短于一拍就被扣穿，表现成"贴着走也不减速"。暂停帧 Δt=0 也不凭空续命。
/// </remarks>

// ✓ 后
/// <remarks>表里没填时长＝在格上持续生效，窗口由 StatusGroup 按物理帧决定；替换成渲染帧 Δt 会被扣穿。</remarks>
```

### 7.3 复述命名的成员注释 → 整行删

```csharp
// ✗ 前
/// <summary>合法格，只有登记过的格能被转换 / 结算；表现层从 Tilemap 枚举地板登记</summary>
private readonly HashSet<Vector2Int> _legal;
```
若该字段名与调用方已经把「只有登记过的格能被转换」表达清楚，**前半句删掉**；
「表现层从 Tilemap 枚举地板登记」是**谁填了这个集合**的事实，属于第 2 节第 1 类，保留成一句。

### 7.4 一行里既有结论又有故事 → 留结论删故事

```csharp
// ✗ 前
// 规则命中但"不改地形"（兜底行的击退这类）：地形不变，效果照样要落地。
// 曾经这里直接 return ⇒ 兜底行的冲量被闷在判定里，"砸中了却什么都不发生"。

// ✓ 后
// 规则命中但"不改地形"（兜底行的击退这类）：地形不变，效果照样要落地。
```

## 9. 常见问题

**Q：接口文件 / 纯枚举文件密度天生很高，也要压吗？**
A：不。预算按文件登记，`comment-budget.json` 里那些文件的上限本来就高
（例：`IEffectTarget.cs` 49.5、`ITileState.cs` 31.6 字符/代码行）。
它们的问题不是"密度高"，而是"有没有第 2 节那 9 类信息"。密度上限只用来判**新文件**。

**Q：生成物里的注释要清吗？**
A：不要。`Generated/**` 由导表镜像覆盖，手改必丢（`AGENTS.md` §3）。
要改就去改 Luban 模板，不要在产物上动手。

**Q：我做功能时顺手加了 5 行注释，`comment-lint` 报超支，但我确实需要它怎么办？**
A：先按 §1 判据逐条删一遍——十有八九能压回预算内。真的压不回去，
说明这个文件承担了新的复杂度，在 PR 里写明理由并 `-Mode seal`，让预算上调被 review 看见。

**Q：`<summary>` 能不能拆成两行？**
A：不能。多行注释块是本规范 §4.2 的硬禁项，`comment-lint` 的标签判定也会把它当违规形态处理。
一行写不下就说明该删的东西还没删干净。
